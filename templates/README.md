# Agent templates

One folder per role, plus `_shared/agents.md`: the operating protocol every agent follows. Values such as
`${SANDBOX_PROJECT}` are placeholders; render them with your `config/factory.env`:

```bash
scripts/render-templates.py            # -> build/templates/<role>/ (git-ignored)
```

## The team

| `factory-analyst` | eval | Antigravity (Gemini 4 Argon) | Hub VM SA | agent activity and issue-flow analysis |
| `search-evaluator` | eval | Antigravity (Gemini 4 Argon) | Hub VM SA | live relevance and latency probes, `eval_runs` |

Mixing harnesses was deliberate (to compare them) and has a cost: each one failed differently (L3 OpenCode model
catalog, L4 Hermes printing instead of messaging, L6 Antigravity hooks, L26 multi-harness upgrade to Gemini 4 Argon). In this run the Claude Code agents (lead,
deployer) had the fewest harness-specific problems.

## Files in a role folder

| File | Scion field | Notes |
|---|---|---|
| `scion-agent.yaml` | the template config | `default_harness_config`, `system_prompt`, `agent_instructions`, `env` (`FACTORY_ROLE` and, for deployers, the sandbox project), `telemetry` |
| `system-prompt.md` | `system_prompt` | what is specific to the role |
| `agents.md` | `agent_instructions` | generated by `render-templates.py` from `_shared/agents.md` (+ the role's `agents.extra.md`, if any) |
| `home/...` | home overlay | copied into the agent's home. The OpenCode and Hermes harness-configs run `sh /home/scion/.local/bin/<harness>-launch.sh`, so the launchers live here. (Note: a stock Scion Hub runs `hermes chat --yolo -c scion-session --create-if-missing` unless `~/.scion/workspace-storage/hubs/<hub-id>/harness-configs/global/hermes/config.yaml` is customized to `base: ["sh", "/home/scion/.local/bin/hermes-launch.sh"]`). |

Harnesses that don't support a native system prompt (OpenCode, Hermes) get the system prompt prepended to the
instructions file; you don't have to do anything about it.

### Names and harness-configs are variables

Templates never hard-code agent names or harness-config names, so one set of templates serves any number of factories
on one Hub (for example one per product of a monorepo):

| Variable | Rendered as | Set by |
|---|---|---|
| `${LEAD_AGENT}`, `${EVAL_LEAD_AGENT}`, … (one per role folder, `<ROLE>_AGENT`) | `<AGENT_PREFIX>-<role>` (`project1-lead`), or the bare role without `AGENT_PREFIX` | `AGENT_PREFIX` in `factory.env` |
| `${CLAUDE_HARNESS}`, `${ANTIGRAVITY_HARNESS}`, `${OPENCODE_HARNESS}`, `${HERMES_HARNESS}` | `<harness>-factory` with a `FACTORY_SUBDIR`, else the bundled name | `FACTORY_SUBDIR` in `factory.env` |
| `${KNOWLEDGE_PLANE}` | `/workspace/<FACTORY_SUBDIR>/knowledge-plane`, or `/workspace/knowledge-plane` without a product folder | `FACTORY_SUBDIR` in `factory.env` |
| `${FACTORY_SUBDIR}` | the product folder (`src/project1`), `.` by default; also the template `env:` that [`factory-cd.sh`](../config/harness/home/.local/bin/factory-cd.sh) reads | `FACTORY_SUBDIR` in `factory.env` |

Write `${<ROLE>_AGENT}` wherever a prompt names an agent (report lines, `scion message` targets, message signatures,
team tables); a test fails on a bare `scion message lead`. Start agents with the names
`scripts/render-templates.py --agent-names` prints. See
[docs/plans/2026-10-22-monorepo-factories.md](../docs/plans/2026-10-22-monorepo-factories.md).

The GCP identity is not part of the template: register the service account in Step 6 and assign `${DEPLOYER_SA}` to the deployer agents in Step 8 of the Hub setup (see
[setup-runbook.md](../docs/setup-runbook.md)).

## Uploading to the Hub

Use [`scripts/push-templates.py`](../scripts/push-templates.py). It renders the roles, ships them to the Hub VM and
creates or updates each template through the Hub API, on top of Scion's default template (the same base
`scion templates create` uses, with its `home/` dotfiles):

```bash
scripts/push-templates.py --project psearch --roles lead,backend,frontend,reviewer,deployer          # dry run
scripts/push-templates.py --project psearch --roles lead,backend,frontend,reviewer,deployer --apply
```

The same procedure gave the five eval templates their own files on 2026-10-13 (the script now reports them up to
date), and it checks that no other template changed.

Each template must have its own files. The original factory seeded its templates by writing rows straight into the Hub
database, and the five eval templates ended up pointing at the `frontend` template's files (L16). Never fix that with
`scion templates push`: a push to an existing template uploads into that row's storage path, so it would have
overwritten the frontend's files. `push-templates.py` renames such a row to `<role>-legacy` and creates a fresh one
instead. Don't edit the Hub DB.

The Scion CLI (`scion templates push <role>` from a checkout linked to the Hub project, `scion templates show <role>`)
also works for templates that own their storage; it wasn't used on this Hub.

Template changes apply when an agent is created. Running agents keep their prompt until they are recreated or
reincarnated (see [operations-runbook.md](../docs/operations-runbook.md#switch-an-agents-harness)); in the meantime, send
the rule change as a message.

## What changed compared with the templates the factory first ran with

- One shared protocol (`_shared/agents.md`) instead of rules copied into every prompt, and `agents.md` no longer
  duplicates the system prompt.
- The old rule "Do NOT run `sciontool status`" is reversed: every agent ends every turn with `sciontool status
  blocked | task_completed | ask_user`, so the Hub stops flagging idle agents as STALLED (L5).
- Agents must see `Message delivered` after `scion message`; printed text reaches no one (L4).
- Evidence on GitHub issues, no invented numbers, real file paths only; the reviewer must cite a file and line or a
  failing command for a FAIL (L4, L9).
- The lead works the backlog on its own (wave order, at most 2 issues in flight), escalates only IAM, cost and scope,
  and never writes product code (L15).
- The deployer records the previous revision, rolls back on failed checks, and deploys as the dedicated runtime SA
  (L7).
- The OpenCode launcher writes a pinned model catalog on every start instead of deleting it (L3).
- The eval team has an explicit data contract: Firestore (`factory_agent_status`, `eval_runs`), GitHub, and the
  bucket; unknown values are shown as "n/a" (L9). The factory control plane never uses Spanner.
- Leftovers removed: `harness: gemini` in the eval templates, `home/.hermes/config.yaml` (the launcher rewrites it on
  every start), `env: SCION_TELEMETRY_ENABLED` (overridden by the Hub, L6).

The [v2 design](../docs/specs/factory-orchestration-v2-design.md) (one worker and one PR per issue, status labels, a
`factoryctl` helper) needs further template changes; these templates are the shared-workspace version that runs
today.
